# Repository overview

Pipa is a Node.js command-line application with Socket and Managed profile modes. Socket Mode connects Slack to one persistent private `opencode serve` process, or to an explicitly configured existing server. Managed mode owns one persistent `opencode serve` child without connecting to Slack. Configuration and Socket Mode session IDs are stored under `~/.pipa`.

This shared-checkout candidate combines native v1/v2 migration work with main's model picker and Slack lifecycle behavior. The current native v2 target to qualify is **2.2.5**, alongside historical v2 **2.0.29** and v1 pins **1.18.35 / 1.19.0**. The SDK remains `@opencode/client@2.0.29` until qualified. This overview describes the integration contract, not evidence that tests, compatibility, migration, or release gates have passed.

## Request flow

1. `bin/pipa.mjs` handles `pipa init` or `pipa start`, loads the profile, and selects Socket or Managed mode.
2. During initialization, `src/app.mjs` validates OpenCode and Slack credentials, warns without blocking when granted-scope metadata omits a recommended Slack scope, then `src/state.mjs` saves the configuration and generated Slack manifest under `~/.pipa`. The manifest includes `channels:read` and `assistant:write` for channel metadata and Chat SDK typing status.
3. During Socket Mode startup, `src/app.mjs` checks that `PIPA_OPENCODE_ATTACH_URL` or one owned OpenCode server on loopback port `0` can serve the configured workspace, then creates the Slack connection, restores previously subscribed Slack threads from `~/.pipa/sessions.json`, reconciles `~/.pipa/routines.json`, and starts the local 30-second routine scheduler. Ordinary v1/v2 detection, listening/readiness and Slack initialization have no default overall startup limit or migration-status gate; OpenCode owns schema/data upgrades, never Pipa. Explicit harness deadlines remain supported; per-request safety timeouts retry, while terminal auth/protocol/wrong-workspace errors fail. Ctrl+C cancels startup and stops owned children, leaving attached servers alive. During Managed startup, `src/opencode.mjs` starts one `opencode serve` child with the profile's working directory, hostname, and port; Managed mode does not execute routines. Detached background restart and shutdown deadlines are unchanged.
4. An authorized mention or subscribed-thread reply, including attachments, is routed to its mapped session. With `mentionOnly` enabled, unmentioned subscribed-thread replies are ignored. V2 serializes prompt admission per Slack thread, then lets native OpenCode steering and background execution continue; it does not interrupt the session for each follow-up. V1 retains interrupt-and-replace behavior. Different threads run independently.
   Existing-thread replies fetch earlier discussion through a direct Slack `conversations.replies` request using the configured bot token. The read runs inside the existing admission lane, uses earlier-than-current timestamps and cursor pagination, and produces bounded quoted user context. It does not call the adapter's history reader or Composio, persist a transcript, or download historical file bodies. New top-level messages skip the read. Missing or partial history is reported rather than invented; cancellation and revoked access still prevent submission.
5. `src/opencode.mjs` checks incoming attachment metadata and downloaded bytes against 10 MiB per file and selects the native adapter. Session mappings are saved before admission. V1 uses prompt system instructions. V2 keeps stable Slack context in native session instructions, sends exact-text prompts with native IDs, and forwards live native events for completed assistant responses. Successful admission is not vetoed by comparing echoed prompt text. Native session moves preserve the mapping and response follower; the configured directory is a starting location, not session confinement. The follower stays attached after the first reply, but does not recover replies missed during a disconnect or restart. Startup restores Slack subscriptions and conversation mappings without reattaching old background work; a new message reattaches its thread. Files retain path, type, identity and size checks; v2's private artifact directory stays in the starting location across moves and background resumptions. Incoming background attachments are admitted as data URIs so deleting local staging cannot break deferred native reads.
6. `src/app.mjs` saves the session ID and posts naturally short text once. Generated files travel with their concise summary in one Chat SDK post; a failed file post receives one text-only retry. Longer inline fallback is split at readable boundaries while preserving fenced code. Existing message reactions still report receipt, success, and failure.
7. Due routines call the same executor with a fresh session, exact saved prompt, configured working directory, and saved Slack channel or thread. After delivery, Pipa binds and subscribes the result thread to that OpenCode session so replies continue it. The scheduler permits different routines to overlap but never overlaps one routine with itself. Every dispatch, interaction, response, and final delivery reloads the relevant authorization. Edits affect future work; deactivation and deletion abort active work. Destination revocation blocks a new run or result delivery at the next authorization check. Shutdown aborts active work and suppresses stale delivery.
8. After full readiness, the CLI watches generation-scoped restart requests. The running Pipa arms a detached worker before cooperative shutdown, awaits cleanup and ownership-aware lock release, and awaits the worker handoff before exiting naturally. The worker waits for the old lock and process, starts the absolute packaged CLI detached, and records success only after replacement readiness IPC. Managed replacements must pass a bounded workspace health check; startup failure stops their owned child and releases the lock before reporting failure. Ordinary Managed starts remain running if health is unavailable, but cannot accept restart requests. Existing Slack authorization is unchanged.

## Files and folders

### `.github/`

GitHub-specific automation.

- `.github/workflows/ci.yml`: Every pull request and push to `main` runs one Ubuntu job: Node.js 22, exact dependencies, unit/integration tests, and installed-package smoke. Manual dispatch runs the same checks on Ubuntu, macOS and Windows for platform/process changes and pre-release verification.
- `.github/workflows/opencode-compatibility.yml`: Manual-only, no-secret pinned native-engine smoke or full qualification matrix. Normal contributor PRs do not launch real engines. Live Slack/client and operator gates remain external qualification evidence.
- `.github/workflows/stats.yml`: Runs daily and on manual dispatch to validate and update the committed npm-download statistics. It uses only `contents: write`, serializes runs, and commits `STATS.md` only when the generated file changed.

### `bin/`

The public command-line entry point installed by npm.

- `bin/pipa.mjs`: Implements the `pipa` command. `pipa init` confirms the working directory, opens Slack's app-manifest setup, reads tokens without displaying them, and calls `initializePipa`. `pipa start` takes a single-instance lock, loads the profile once, and starts either the existing Slack application or the Managed OpenCode server. `pipa routine` parses the six routine lifecycle commands, exact prompt input, schedules, previews, and stable JSON output. It forwards `SIGINT` and `SIGTERM` before releasing the lock. `pipa --version` reads the version from `package.json`. `pipa restart` requests an asynchronous detached restart, and `pipa restart --status` provides read-only inspection of its durable outcome.

`pipa manifest` is a read-only existing-profile CLI command. It loads local config and prints a fresh manifest template without credentials, API calls, inference, lock acquisition, or state writes. It does not fetch or modify remote Slack configuration; operators merge desired command/scope additions into the existing app.

### `docs/`

Long-form repository documentation.

- `docs/assets/`: README banner and the GitHub social-preview source. These are presentation assets, not runtime files.
- `docs/repository-overview.md`: This file. It explains the repository structure and how the application works.
- `docs/opencode-compatibility.md`: Version/capability policy, existing-profile upgrade, deliberate v2 migration, matched-snapshot rollback and private operator checklist.
- `docs/pipa-testing.md`: Deterministic/native/live lanes, isolated profiles, live evaluator inputs, evidence and cleanup.

### `scripts/`

Repository maintenance and release checks that are not part of the installed runtime.

- `scripts/pack-smoke.mjs`: Tests the package users will actually receive. It packs and installs the archive in a temporary directory, verifies version, routine help and side-effect-free preview, Local initialization, and cancellation, then starts a Managed profile with a fake OpenCode executable that checks arguments, working directory, and inherited environment without Slack credentials. It removes the temporary artifact when finished.
- `scripts/stats.mjs`: Fetches validated npm download data for `@usepipa/pipa` and appends one completed UTC-day snapshot to `STATS.md`. It fails without changing existing statistics when the source data or prior file is unsafe.
- `scripts/test-opencode-matrix.mjs`: Installs an integrity-checked candidate and exact native pins privately, runs shared semantic cases and optional migration/rollback, and records honest deterministic/release gates.
- `scripts/slack-release-eval.mjs`: Opt-in serial live collector reusing the semantic catalog and routine flow; new/existing thread continuation, both routine destinations, optional independently observed restart and explicit blocked human/integration gates.
- `scripts/slack-routine-eval.mjs`: Import-inert reusable preview/confirmation/scheduled-result flow; validates exact saved input, lifecycle, session continuation, duplicate observation and nonce-only cleanup.
- `scripts/verification/slack-eval.mjs`: Shared authenticated preflight, paginated/rate-limited Slack reads, credential-clean CLI calls, app-scoped local lock and durable restart observation. Candidate process ownership stays with the operator.

### `src/`

The application implementation.

- `src/models.mjs`: Registers one private native Slack model picker for both the normalized name command (`Chopper` -> `/chopper model`) and `/pipa model`. Manifest generation and startup share `src/state.mjs`'s `slackCommandNames` list, deduplicated for Pipa; startup validates names before opening Slack/OpenCode resources. Usage/error recovery points to the primary named command, and the modal label identifies the installation. Slack registration is still required and alias collisions route to the most recently installed app. Opaque, user/view-bound contexts carry opening-channel authorization through search and Save, expire after 30 minutes, and clear on shutdown. Catalog discovery is authenticated and workspace-scoped: v2 has no Pipa-added deadline; v1 has a 30-second catalog limit after server readiness. A loading window opens before discovery, then becomes a native external select. Each context caches search text, opaque choices, and model IDs for the full catalog; options callbacks recheck authorization and return up to 100 matches without OpenCode calls. Model names, IDs and providers are searched case-insensitively with all terms required. Catalog size and provider ordering do not limit availability; empty catalogs get a private explanation. Native views preserve the SDK's private-metadata envelope for submission routing. Save rechecks current authorization and resolves the cached choice, then persists through `src/state.mjs`'s serialized narrow config mutation without catalog rediscovery. Ordinary turns pass the current `defaultModel` as a fallback for new/empty sessions; the executor reuses the latest message's model for existing sessions, including after restarts. A missing OpenCode session is replaced using the current default. Routine create/preview snapshots the default into an optional immutable record field, and routine dispatch uses only that explicit snapshot. No picker action creates an OpenCode session or runs inference.

  The picker exchanges the short-lived Slack trigger for a loading view before discovery, then updates that view with choices. Save acknowledges by closing promptly; tracked background work validates and persists the choice and delivers a private result to the opening channel. Duplicate submissions do not duplicate writes. Closing or discarding a picker aborts pending discovery and suppresses its later update; shutdown invalidates contexts and drains pending saves before disconnecting Slack. Picker errors retain the original message with existing Slack-token redaction, without attached bodies or stacks.

- `src/app.mjs`: Coordinates Slack, OpenCode, persisted sessions, and local routine delivery. `initializePipa` validates input and credentials before saving configuration and reports recommended missing Slack scopes without blocking. `startPipa` creates the Slack adapter, restores thread subscriptions, filters unsupported messages, enforces file limits, sends prompts and attachment descriptors to OpenCode, starts active-turn typing status, posts inline or artifact-backed responses, starts Socket Mode routine execution, and handles startup cancellation, explicit harness startup deadlines and bounded shutdown. Routine interactions and results reuse the same Slack helpers with fresh destination and responder authorization. `createConversationRunner` serializes work within each thread while allowing separate threads to run concurrently.
  `createPipaSlackAdapter` contains a compatibility boundary for the pinned Slack adapter: shutdown detaches Socket Mode ingress, drains accepted event acknowledgments for up to three seconds, then disconnects. External-select responses are capped at 12 KiB after native serialization: live 19 KiB responses stalled delivery and broke subsequent Saves, while the smaller budget passed repeated search/Save trials. This is a conservative tested budget, not a documented Slack maximum; narrower searches still cover the full cached catalog. Event rejections are observed locally with credential-free diagnostics so they cannot bypass CLI lock cleanup through an unhandled rejection.
  Model commands dispatch with the Slack payload's user/channel IDs without awaiting optional `users.info` enrichment, so a cold profile lookup cannot expire the modal trigger. Other commands retain the SDK's normal routing. Model Save acknowledges after synchronous context checks; fresh config authorization, cached choice lookup, and persistence run in tracked background work.
- `src/opencode.mjs`: Owns authenticated runtime selection, the shared executor/controller registry, attachment staging, trusted instruction construction, artifact safety/cleanup, and child-process boundaries. Socket Mode checks the configured workspace before connecting Slack; Managed mode starts the server-only profile. Owned children inherit the runtime environment except Slack credentials. Windows termination uses `taskkill` to stop descendants.
- `src/opencode-v1.mjs`: Owns native v1 session resolution, prompt/status/message reconciliation, event-driven questions and permissions, and server cancellation.
- `src/opencode-v2.mjs`: Uses pinned `@opencode/client@2.0.29` for native session admission and live event following. Slack response observers outlive individual requests and receive later background completions. No response-history resync, delivery replay, custom attribution guard, temporary instruction cleanup, recovery journal, or installation-wide blocked flag is used. Reconnect rechecks session identity and pending interactions, not past responses or a frozen directory. Interaction reconciliation discovers native descendants and reads session-scoped forms/permissions across moves. Interaction network work is queued per observer so it cannot block other sessions' response events. Native question forms and permissions retain authorized Slack controls; native ancestry, not directory equality, determines ownership. Both adapters expose `interaction.submit(decision)` and `interaction.settled`; native refusal leaves controls editable. Richer forms remain native-client-only. See the [runtime-check assessment](native-behavior-checks.md) for removed vetoes and retained integration checks.
  Before current-request execution, existing-session resolution checks the native working location. Only a matching typed missing-location result permits a one-attempt move to the native-resolved starting folder, with no observed active or queued work and confirmation of the applied target. The shared executor reports confirmed recovery through an optional callback before model/instruction/prompt writes. These reads do not lock other native clients. Unconfirmed moves and uncertain admissions are not retried; no prompt-time error launches another recovery path. Normal moves outside the starting folder remain valid.
- `src/routines.mjs`: Owns routine validation, IANA timezone schedules, strict-future recurrence, private atomic state mutation, restart reconciliation, conditional outcome merges, per-routine overlap prevention, and the non-overlapping scheduler tick. `routines.json` and its short-held mutation lock live separately from Pipa's process lock and session state.
- `src/restart.mjs`: Owns immutable restart requests, read-only durable status, bounded worker IPC, and detached relaunch. `pipa restart` and `pipa restart --status` use this module; private records live in `.pipa/restarts`. Workers and owned OpenCode children inherit a credential-cleaned environment with the same resolved `PIPA_HOME`. Agent context advertises the CLI and its asynchronous outcome. Detachment survives the agent turn ending; `/instance/dispose` cannot substitute for a server restart. Attached servers stay unowned.
- `src/state.mjs`: Owns local state and the Slack app manifest. It defaults profiles without `slackMode` to `socket`, validates shared and mode-specific fields, writes private JSON files atomically, loads sessions, serializes session writes, and uses a lock file to prevent two Pipa instances from controlling the same local state.

### `test/`

Tests run by Node's built-in test runner through `npm test`.

- `test/app.test.mjs`: Tests application orchestration: safe initialization, Slack token and scope handling, per-thread queueing, typing lifecycle, session continuity, attachment routing and limits, Slack filtering and delivery, routine execution and cancellation, interaction authorization, artifact fallback, reactions, secret redaction, readable chunking, and startup and shutdown cleanup.
- `test/cli.test.mjs`: Tests the routine CLI lifecycle, side-effect-free preview, schedule normalization, exact prompt files, JSON output, and destination allowlist enforcement through isolated subprocesses.
- Restart CLI coverage also launches isolated Managed fake servers, verifies PID/generation replacement and survival after worker exit, and checks failed/unready replacement cleanup. `test/restart.test.mjs` covers orchestration and handoffs with controlled process boundaries. Package smoke verifies installed restart help/status and worker availability.
- `test/opencode.test.mjs`: Tests owned and attached server selection, authentication, native session completion, stale-session recovery, attachment and artifact cleanup, artifact parsing and file safety, Slack-only delivery guidance, secret removal, timeout behavior, and cross-platform child lifecycle.
- `test/routines.test.mjs`: Tests schedule and DST boundaries, private atomic routine state, mutation locking, restart recovery, conditional merges, run requests, scheduler overlap, cancellation, and shutdown races.
- `test/state.test.mjs`: Tests state management: Socket and Managed profile validation, Slack manifest generation, private file permissions, separate configuration and session storage, malformed state errors, recovery after failed writes, and single-instance locking.
- `test/models.test.mjs`: Exercises native SDK/Slack adapter slash commands, cached search choices, modal Save/reopen/Cancel, and default changes while reusing the same session, plus denied/expired callbacks, discovery/write errors, cached Save during catalog outages, and bounded search responses from large interleaved catalogs. Executor tests in `test/opencode.test.mjs` verify existing-thread model retention. Native deadline regressions hold config reads and cold `users.info` calls to verify acknowledgment and opening do not wait on them. Only outbound Slack APIs are replaced in the native routing test.

Native and live qualification must use isolated Pipa profiles and separate OpenCode HOME/XDG, database, configuration, and supported platform-specific storage paths. `PIPA_HOME` alone does not isolate OpenCode. Migration uses stopped, matched snapshots and disposable copies; rollback restores both pristine Pipa and OpenCode state, never opens v2-written storage in v1, and never discards recovery journals to bypass blocked intake. See the linked testing and compatibility guides for the full procedure; historical pin lists and deferred-picker statements there must not be read as the current target or integrated picker status.

### Root files

- `.gitignore`: Keeps generated dependencies, package archives, local environment variables, macOS metadata, and local OpenCode state out of Git.
- `STATS.md`: Public daily npm package download snapshots. Counts are not installs, users, active users, or conversions.
- `CONTRIBUTING.md`: Gives contributors the supported Node.js version, local verification commands, and expectations for focused changes and secret handling.
- `LICENSE`: Contains the Apache License 2.0 terms under which Pipa is distributed.
- `SECURITY.md`: States the local security model, supported versions, scope, and the private vulnerability-reporting path.
- `package-lock.json`: Locks the full npm dependency graph to exact versions so local development and CI install the same packages.
- `package.json`: Defines package metadata, the `pipa` executable, published files, npm scripts, supported Node.js version, dependencies, repository links, and license identifier.
- `README.md`: Provides the visual hero, product description, security summary, requirements, installation and usage instructions, command reference, development commands, release policy, and license link.
